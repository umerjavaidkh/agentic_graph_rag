USING THE SCHEMA:
- Use only labels, relationships and properties that appear in the schema
- A property belongs to the node or relationship the schema lists it under.
  Reading a node's property off a relationship variable returns null, not an
  error, so the query silently reports 0 or null as if it were the answer. If
  the measure you need is on a node, bind that node and read it from there
- Relationship direction is critical. If the schema lists (:A)-[:R]->(:B),
  match (a:A)-[:R]->(b:B) and never reverse the arrow unless the question
  explicitly asks for the inverse
- Multi-hop questions: chain patterns using schema directions. Each
  relationship must connect the node types shown in its schema pattern --
  never attach a relationship to a label absent from that pattern
- If an entity is not its own node here, it may be a property on a related
  node. Group or filter on that property instead of inventing a label
- Counting real-world entities: group by the PROPERTY that identifies them,
  not by the node. VALUE SETS AND CARDINALITY says which is which -- a
  property with fewer distinct values than there are nodes repeats, so it is
  the natural key, while one with exactly as many is a per-row id. Graphs
  loaded from transactional tables often carry one node per transaction, so
  grouping by the node makes every entity look like it appears once
- Match text values case-insensitively with toLower() and CONTAINS. When two
  properties hold the same concept in different forms (a code and a label, or
  two languages), match against the one whose values look like the value in
  the question

CYPHER SYNTAX:
- Cypher does NOT support SQL GROUP BY. Use WITH to aggregate and group
- Do NOT use SQL window functions: ROW_NUMBER() OVER, RANK() OVER,
  PARTITION BY, OVER (...)
- For "top N per group": aggregate per entity with WITH, ORDER BY groupKey,
  metric DESC, then collect the rows per group and slice the first N with
  rows[0..N-1]. Never use window functions
- Every expression in WITH must be aliased with AS
- Never nest MATCH inside RETURN. Use multiple WITH stages, or return
  aggregated maps/lists only
- Alias results after what they actually measure. Never label one property as
  a different concept
- Prefer one focused query. If the question has several parts, answer the main
  ranking or aggregation first

NUMBERS AND DATES:
- Wrap numeric fields with toFloat() or toInteger() before arithmetic, since
  imported columns are often stored as strings. This applies to NUMBERS only:
  a property typed DateTime is already a temporal value, and converting one
  through toInteger()/epochMillis is a type error, not a safety measure --
  pass it straight to duration.inDays() or compare it directly
- Revenue and totals: sum the monetary property the schema actually has,
  multiplying by a quantity property only when one exists
- Use COUNT(DISTINCT node) when counting entities that repeat across joins
- Aggregations and rankings ("most", "highest", "top"): MATCH the full path,
  WITH groupKey, the aggregate AS metric, then RETURN groupKey, metric
  ORDER BY metric DESC LIMIT {n}
- Elapsed days is duration.inDays(earlier, later).days. Do NOT use
  duration.between(a, b).days for this: `.days` on a general duration is the
  day component left after whole months are removed, so a 45-day gap reads as
  15. Measured on real data it understated every state's delivery time and
  changed which state ranked first -- a wrong answer that looks entirely
  plausible. Use duration.inDays for a total, and aggregate with avg()
  directly rather than collect() plus apoc.coll.avg().
- Duration argument order: duration.inDays(earlier, later) and
  duration.between(earlier, later) take the EARLIER instant first. Reversing
  them returns a negative elapsed time, which is never the answer to "how
  long between X and Y" -- if your result would be negative, the arguments
  are the wrong way round, not the data
- Do not truncate per row before aggregating. toInteger(...) inside an
  average discards each row's fraction and biases the mean downward; average
  the raw values and round the final result instead
- For dates that include a time, parse via substring(toString(prop), 0, 10)
  before date()
- For month or day bucketing use substring(toString(prop), 0, 7) for YYYY-MM
  or substring(toString(prop), 0, 10) for YYYY-MM-DD -- never
  apoc.date.format(), which expects epoch-millis and throws on a date value

PRESENTING ROWS:

  a category or type name), join to it and return that too. If the only
